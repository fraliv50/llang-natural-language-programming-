# Terminal / Shell Semantic Reference Matrix (Nushell grounding)

**Purpose.** Grounding reference for rebuilding llang's *shell / terminal-command layer*. Per `docs/METHOD.md`, we never invent semantics: we re-express an authoritative language's semantics behind an English surface. This matrix maps Nushell's command/shell constructs to precise semantics, documented gotchas, and **candidate** llang phrasings. Every claim is traceable to the official Nushell Book. Surface phrasings are **candidates, not a final grammar** — where this doc disagrees with the implementation, **the code wins** (`METHOD.md` §Pitfalls, "documentation drift"; `DESIGN.md` §5).

**Authority / provenance.** Official Nushell Book and linked sub-pages, retrieved 2026-11-22 from `www.nushell.sh/book/`, project source `github.com/nushell/nushell`. Nushell and its documentation site are **MIT licensed** ([LICENSE](https://github.com/nushell/nushell/blob/main/LICENSE)); we cite prose and reproduce no code verbatim. Notation: `Nu:` = Nushell behavior; `⇒` = semantically equivalent; `≈` = approximately (differences noted); `Surface:` = candidate llang phrasing; **bold** = recommended primary candidate. Page anchors are linked inline.

**Source pages:** [Thinking in Nu](https://www.nushell.sh/book/thinking_in_nu.html) · [Pipelines](https://www.nushell.sh/book/pipelines.html) · [Types of Data](https://www.nushell.sh/book/types_of_data.html) · [Running External Commands](https://www.nushell.sh/book/running_externals.html) · [Stdout, Stderr, Exit Codes](https://www.nushell.sh/book/stdout_stderr_exit_codes.html) · [How Nushell Code Gets Run](https://www.nushell.sh/book/how_nushell_code_gets_run.html) · [Modules](https://www.nushell.sh/book/modules.html) (+ [Using](https://www.nushell.sh/book/modules/using_modules.html) / [Creating](https://www.nushell.sh/book/modules/creating_modules.html)) · [Custom Commands](https://www.nushell.sh/book/custom_commands.html).

## 1. Why Nushell is the reference; license; scope of copying

**Why Nushell.** Python grounded llang's general-purpose core (values, closures, exceptions, collections — `docs/research/python-semantics.md`). The shell/command layer needs a *different* authority because the hard questions here are not Python questions: what flows through a pipeline, how external bytes become values, how stdout/stderr/exit codes are modeled, how cwd/environment are scoped, how external commands are resolved, and how commands and modules are declared. Nushell is the strongest public specification of exactly this "structured shell" model: it is a shell *and* a programming language with an explicit data model, and — critically for our method — its docs settle every hard case with prose we can cite, so we spend effort on phrasing, not guessing ([Thinking in Nu — "Nushell isn't Bash"](https://www.nushell.sh/book/thinking_in_nu.html#nushell-isn-t-bash)).

The choice is also a good *semantic fit* for llang: Nushell pipelines carry structured **lists/records/tables**, and llang already has **lists/maps** and dynamic values (`DESIGN.md` §2–3, `docs/GRAMMAR.md`). A shell built on "commands return values" rather than "commands write text" composes with our existing `call NAME with label = expr` and map/list literals with almost no new core semantics — exactly the tier-preserving strategy of `docs/FAMILY-PLAN.md` ("modules extend values/types, never syntax").

**License.** Nushell and `nushell.github.io` are MIT licensed; re-expressing documented semantics and citing prose is permitted. We copy **ideas, invariants, and terminology**, not source code, not command implementations, and not documentation text.

**What we ARE copying (semantics only):**
- The *value model of the shell*: every command returns a value; data (not text) flows between internal stages; raw bytes cross the external boundary and are decoded ([Thinking in Nu — Every Command Returns a Value](https://www.nushell.sh/book/thinking_in_nu.html#every-command-returns-a-value); [Pipelines — Working with External Commands](https://www.nushell.sh/book/pipelines.html#working-with-external-commands)).
- The *stream/redirection model*: producer → filter → sink, `$in`-style pipeline input, stdout / stderr / exit-code separation, `pipefail`, `complete`-style capture ([Pipelines — Basics](https://www.nushell.sh/book/pipelines.html#basics); [Stdout, Stderr, Exit Codes](https://www.nushell.sh/book/stdout_stderr_exit_codes.html)).
- The *resolution and safety model*: explicit external-vs-internal sigils, PATH lookup only after internal resolution, allowlisted foreign bridge, scoped environment ([Running External Commands — How Nushell finds a command](https://www.nushell.sh/book/running_externals.html#how-nushell-finds-a-command); [Thinking in Nu — Environment is Scoped](https://www.nushell.sh/book/thinking_in_nu.html#nushell-s-environment-is-scoped)).
- The *parse-before-eval discipline*: no `eval`, everything known before execution; localized errors and lint ([How Nushell Code Gets Run](https://www.nushell.sh/book/how_nushell_code_gets_run.html); `DESIGN.md` §5–6).

**What we are NOT copying:**
- Nushell syntax (`|`, `^`, `%`, `o+e>`, `$env.X`, `{ ... }` closures) — we re-express it in llang's closed English vocabulary.
- The Nushell implementation (Rust engine, parser, REPL, reedline) and its builtin command catalog.
- Its static type-annotation system, `record`/`table`/`binary`/`duration`/`filesize`/`cell-path` value types, config tables, and plugin ecosystem (see §4).
- Nushell's *interactive* surface — prompt, colors, completions, keybindings, line editing (that is the terminal-emulator/UI concern, §5).

## 2. Cross-cutting invariants (read first)

These are the load-bearing rules. Write them into the canonical core before any syntax.

1. **A command is a value-returning expression, not a side-effecting statement.** In Nu, "every command returns a value, even `null`"; `let` returns `null`, `print` returns `null` yet forces display; implicit return means the *last* expression of a pipeline or custom command is its value ([Thinking in Nu — Implicit Return](https://www.nushell.sh/book/thinking_in_nu.html#implicit-return), [Single Return Value per Expression](https://www.nushell.sh/book/thinking_in_nu.html#single-return-value-per-expression), [Every Command Returns a Value](https://www.nushell.sh/book/thinking_in_nu.html#every-command-returns-a-value)). `echo 1 2 3` returns a list; `echo` with no args returns `""`; `(echo "x") == "x"`. **llang consequence:** a shell call's result must be an expression value — recommend a map (`"output"`, `"errors"`, `"exit code"`) or plain text — so `set result to call shell ...` works. Do not model shell calls as statements that only print.

2. **Only the last value is returned; earlier expression values are discarded.** `40; 50; 60` returns 60; `echo "msg"` on a non-final line is silently dropped, so use `print` to display ([Thinking in Nu — Single Return Value](https://www.nushell.sh/book/thinking_in_nu.html#single-return-value-per-expression)). **llang consequence:** llang's explicit `give back` already avoids this ambiguity for functions; the shell layer must not reintroduce "hidden intermediate values." A pipeline stage's value must be explicit.

3. **Data flows through pipelines as structured values; text is the boundary format.** Internal Nu commands exchange Nu data types (int, string, list, record, table, …); when data goes *into* an external, a string is sent as-is (no added newline), binary as raw bytes, and lists/records/tables are rendered by `table` (bordered!) unless converted with `to text`; `null` sends nothing and other singles must be converted with `into string`. Data coming *from* an external arrives as a byte stream, auto-decoded to UTF-8 text or left binary ([Types of Data](https://www.nushell.sh/book/types_of_data.html); [Pipelines — Working with External Commands](https://www.nushell.sh/book/pipelines.html#working-with-external-commands)). **llang consequence:** crossing to the host must be an explicit, typed conversion — never implicit `table` rendering. This is the same "no implicit coercion" rule as `DESIGN.md` §5.3.

4. **stdout, stderr, and exit code are three separate channels.** By default Nu redirects an external's stdout into a pipeline but leaves stderr on screen; non-zero exit is an error that stops a script; `complete` captures `{stdout, stderr, exit_code}` in one record ([Stdout, Stderr, Exit Codes](https://www.nushell.sh/book/stdout_stderr_exit_codes.html); [Pipelines — Failing External Commands](https://www.nushell.sh/book/pipelines.html#failing-external-commands-in-a-pipeline)). **llang consequence:** the shell-call result must carry all three; a non-zero exit must not be silently conflated with textual output.

5. **`pipefail`-style failure is the default: any failing stage fails the whole pipeline**, even if later stages succeed; `LAST_EXIT_CODE` holds the rightmost failing external's code (signals reported negative, e.g. SIGTERM → `-15`); opt-out exists but we adopt the safe default ([Pipelines — Failing External Commands in a Pipeline](https://www.nushell.sh/book/pipelines.html#failing-external-commands-in-a-pipeline); [Stdout, Stderr, Exit Codes — Exit Code](https://www.nushell.sh/book/stdout_stderr_exit_codes.html#exit-code)).

6. **Environment and cwd are scoped, not global mutable state.** Nu closures and custom commands own their environment; `cd` inside a `def` or closure is discarded on exit; blocks of `if`/`match`/`for`/`while`/`loop`/`try` are *not* closures and DO persist env changes; `def --env` is the explicit opt-in to mutate the caller ([Thinking in Nu — Environment is Scoped](https://www.nushell.sh/book/thinking_in_nu.html#nushell-s-environment-is-scoped); [Custom Commands — Changing the Environment](https://www.nushell.sh/book/custom_commands.html#changing-the-environment-in-a-custom-command)). **llang consequence:** host cwd/env changes from a shell call are local by default; persistence requires an explicit construct. This also underpins the safety model (§6).

7. **Parse the whole unit before evaluating any of it; there is no `eval`.** Nu is "parsed entirely, then evaluated entirely"; parser-keywords like `use`/`source` resolve at parse time, so the file/cwd must exist *before* the line runs; only restricted, side-effect-free parse-time constants (`const`) may be evaluated early ([Thinking in Nu — Think of Nushell as a Compiled Language](https://www.nushell.sh/book/thinking_in_nu.html#think-of-nushell-as-a-compiled-language); [How Nushell Code Gets Run](https://www.nushell.sh/book/how_nushell_code_gets_run.html)). **llang consequence:** fits `DESIGN.md` §5 (linter before execution, localized errors); shell module paths and flag schemas must be resolvable statically; no dynamic command-source execution.

8. **Errors are loud, source-located, and typed by kind.** Nu distinguishes parse errors (`nu::parser::*`) from shell/runtime errors (`nu::shell::*`) and attaches spans + "Did you mean …" help; duplicate definitions, shadowed keywords, unknown flags, wrong types are all parse-time failures ([Running External Commands](https://www.nushell.sh/book/running_externals.html#how-nushell-finds-a-command); [Custom Commands — Naming](https://www.nushell.sh/book/custom_commands.html#naming-commands)). **llang consequence:** map failures to existing `fail with KIND, "msg"` / `expect … if a problem of kind …` with a `require`-style assertion layer; never guess-and-continue.

9. **External-vs-internal resolution is explicit and ordered.** Bare name → alias/custom command/builtin first; an external on `PATH` is used *only* if nothing internal matches; `^` forces external, `%` forces builtin; a same-name custom command shadows a builtin ([Running External Commands — How Nushell finds a command](https://www.nushell.sh/book/running_externals.html#how-nushell-finds-a-command); [Custom Commands — Shadowing](https://www.nushell.sh/book/custom_commands.html#shadowing-built-in-commands)). **llang consequence:** llang must never fall through to a host executable by bare name; host execution is an explicit, labeled opt-in (§6).

## 3. Construct-by-construct matrix

For each construct: **Nu semantics → documented gotchas → candidate llang phrasing.** All phrasings must round-trip through canonical nodes and the closed vocabulary (`METHOD.md` steps 4–5); any new label is validated against a registry (pitfall: "silent acceptance of extra arguments").

### 3.1 Command invocation

- **Nu semantics.** Calling a command is evaluating an expression that returns a value. Pipelines have producer/filter/sink roles ([Pipelines — Basics](https://www.nushell.sh/book/pipelines.html#basics)). A command may be internal (builtin, custom, alias) or external (`^`), resolved in that order; the `^` sigil calls the executable found on `PATH` ([Running External Commands](https://www.nushell.sh/book/running_externals.html)). Command names may be multi-word strings (`"str stats"`), separated by single spaces; parser keywords cannot be command names ([Custom Commands — Naming Commands](https://www.nushell.sh/book/custom_commands.html#naming-commands)).
- **Gotchas.** `>` is a *comparison operator* in Nu, not redirection: `echo "h" > f.txt` passes three args and writes nothing — use `save` or `o>` ([Thinking in Nu — "But it's not Bash"](https://www.nushell.sh/book/thinking_in_nu.html#but-it-s-not-bash)). `&&`/`||` are parse errors in Nu (`;` / `try-catch` instead). Piping into a command that ignores input (e.g. `ls`) silently discards it or errors; check `help <cmd>` input/output types ([Pipelines — Command Input and Output Types](https://www.nushell.sh/book/pipelines.html#command-input-and-output-types)). Semicolons discard earlier stage output (`ls; "x"` → only `"x"`).
- **Candidate phrasing.** Native llang calls already use `call NAME with label = expr`; a host-shell call must be explicitly marked:
  - **`call shell with command = "git status --short"`** (returns a result map) — or, with a structured argument, **`call run from shell with program = "git", arguments = a list of "status", "--short"`** (argv form; see §6 — argv preferred over a single interpolated string).
  - `use the foreign shell module` makes the names available; qualified `call ... from shell` mirrors `use the foreign json module` / `call dumps from json with value = payload` (`examples/modules.ll`). Keep the `foreign` marker: shell execution is not llang-native.

### 3.2 Flags / parameters (named arguments)

- **Nu semantics.** Custom-command signatures declare positional parameters (required by default; `?` optional/⇒ `null`; defaults allowed but must be parse-time constants), **named flags** (`--age: int`, shorthand `--age (-a)`, boolean switches), and a single trailing rest parameter (`...names: string`). Flags can precede or follow positionals; flags share the variable namespace with parameters; `--` ends flag parsing; `...$record` spreads fields as named flags ([Custom Commands — Parameters](https://www.nushell.sh/book/custom_commands.html#parameters), [Flags](https://www.nushell.sh/book/custom_commands.html#flags), [Rest parameters](https://www.nushell.sh/book/custom_commands.html#rest-parameters), [Passing Flags from a Record](https://www.nushell.sh/book/custom_commands.html#passing-flags-from-a-record)). Every command automatically has `--help`/`-h`; `--help` cannot be redeclared.
- **Gotchas.** `--caps true` is an `extra_positional` error — switches use `--caps=true` (space vs `=` matters). `--all-caps` creates `$all_caps` and collides with a parameter named `all_caps`. Required-after-optional and duplicate names are parse errors. A default from a `let` is not constant; use `const`. Type annotations are a parse-time feature; boolean switches cannot be annotated `: bool`. `--` reaches externals unchanged but is stripped for builtins ([Custom Commands — Flags](https://www.nushell.sh/book/custom_commands.html#flags); [Running External Commands — Passing Arguments](https://www.nushell.sh/book/running_externals.html#passing-arguments)).
- **Candidate phrasing.** llang's labeled calls already are the named-argument mechanism and dodge the space-vs-`=` trap:
  - **`call shell with program = "git", arguments = a list of "commit", "-m", "Update docs", flags = a map with "verbose" mapped to true`**.
  - Treat the labels as a **closed registry** per command; unknown label ⇒ parse/lint error with "did you mean …". This is directly the `METHOD.md` guard against silent acceptance of extra arguments. We do **not** copy `-a`/`--caps` spellings (symbols are outside llang's closed vocabulary); shorthand belongs in `synonyms.py` as words if ever needed, never as sigils.

### 3.3 Pipelines

- **Nu semantics.** A pipeline is input → filter(s) → output; `|` connects stages and carries structured data ([Pipelines — Basics](https://www.nushell.sh/book/pipelines.html#basics)). The special `$in` variable is the current pipeline input; it collects a stream into a value (forcing completion/memory) ([Pipelines — `$in`](https://www.nushell.sh/book/pipelines.html#pipeline-input-and-the-special-in-variable)). Stage forms: single value, list stream, byte stream; filters like `each` preserve streaming, `sort`/`reverse`/`length`/`collect` force collection ([Custom Commands — Streaming and collecting input](https://www.nushell.sh/book/custom_commands.html#streaming-and-collecting-input)). Semicolons/newlines separate expressions and discard non-final values ([Thinking in Nu — Single Return Value](https://www.nushell.sh/book/thinking_in_nu.html#single-return-value-per-expression)).
- **Gotchas.** A newline ends a pipeline unless it ends with `|` or the next line starts with `|`; a blank line ends it ("Command does not support nothing input"). An operator at line end is an "Incomplete math expression" error — wrap in parentheses ([Pipelines — Multi-line pipelines](https://www.nushell.sh/book/pipelines.html#multi-line-pipelines)). `$in` is `null` with no input; using `$in` for a *stream* collects it (large streams cost memory); `open f | save -f f` fails unless you `collect` first ([Pipelines — Collectability of `$in`](https://www.nushell.sh/book/pipelines.html#collectability-of-in)). Between two externals, `|` is plain OS stdout→stdin like Bash. Data rendered to an external gets bordered `table` text unless converted with `to text` ([Pipelines — Output Result to External Commands](https://www.nushell.sh/book/pipelines.html#output-result-to-external-commands)).
- **Candidate phrasing.** Pipelines are a **new** construct — recommend an explicit, visible stage form rather than importing `|` (consistent with `DESIGN.md` §11 "keep structure visible"):
  - **`pipe the value of call shell with command = "cat names.txt" into call shell with command = "sort"`** (candidate), or a block form:
    ```
    with the output of call shell with command = "ls" as input
        call shell with command = "wc -l"
    end with
    ```
  - For `$in`, recommend an explicit label **`with input = expr`** on the consuming call, or bind the pipeline input with `set items to the incoming value` (a reserved phrase), rather than an implicit `$in` whose meaning shifts by position. Llang's one-statement-per-line rule (`GRAMMAR.md`) avoids Nu's multiline `|` hazards; we should still forbid silently-ending a pipeline with no sink. **Note:** streaming is an optimization; v1 may collect fully — document it, don't guess.

### 3.4 Redirection (stdout / stderr / files)

- **Nu semantics.** A plain `|` redirects an external's stdout to the next command. stderr stays on screen by default; `e>|` pipes stderr, `e> file` writes it to a file, `o+e>` (or `out+err>`) combines streams, `o>>` appends, `o+e>|` pipes both ([Stdout, Stderr, Exit Codes — Stderr / File Redirections / Pipe Redirections](https://www.nushell.sh/book/stdout_stderr_exit_codes.html)). `complete` gathers `{stdout, stderr, exit_code}` in one record; its `stdout`/`stderr` are strings (UTF-8) or `binary` when invalid ([Stdout, Stderr, Exit Codes — complete](https://www.nushell.sh/book/stdout_stderr_exit_codes.html#using-the-complete-command)). `print` writes straight to Nu's own streams and is not captured by file redirection; `ignore` discards output and (by default) also ignores non-zero exit ([Stdout, Stderr, Exit Codes — echo/print/log, Discarding Output](https://www.nushell.sh/book/stdout_stderr_exit_codes.html)).
- **Gotchas.** `>` is not redirection ([Thinking in Nu](https://www.nushell.sh/book/thinking_in_nu.html#but-it-s-not-bash)). Naming one file for both streams (`o> f e> f`) makes them overwrite each other — use `o+e>`. A redirection with no command (`ls | o> f`) is an error; `def`/`use`/`module`/`for` cannot be redirected; pipe redirection affects only the *last* command in an expression. Redirected output of a failing external may be lost — use `complete`. `o>|` is a parse error (plain `|` already pipes stdout).
- **Candidate phrasing.** Prefer a result map over sigils:
  - **`set result to call shell with command = "cat missing.txt", capture stderr = true, capture output = true`** ⇒ a map with `"output"`, `"errors"`, `"exit code"` mapped to text/number. Reading a field: **`show item "errors" of result`**.
  - File redirection as labeled parameters, not operators: **`call shell with command = "make", write output to = "build.log", append errors to = "build.err"`**. Paths must be strings; reject a non-string path (Nu's `cant_convert`). Combine streams with a single label **`write both streams to = "all.log"`** (no double-open bug).
  - `ignore` equivalent: **`call shell with ... , discard output = true, ignore failure = true`** — but default to NOT ignoring failure (see invariant 5).

### 3.5 Variables

- **Nu semantics.** `let` (immutable), `mut` (mutable), `const` (parse-time); variables use `$name`; environment is `$env.NAME`; `$in` is pipeline input ([Thinking in Nu — Variables are Immutable by Default](https://www.nushell.sh/book/thinking_in_nu.html#variables-are-immutable-by-default); [Types of Data — Nothing](https://www.nushell.sh/book/types_of_data.html#nothing-null)). `let` can be a pipeline stage (passes input through unchanged); `mut`/`const` cannot ([Pipelines — Assigning Pipeline Results with `let`](https://www.nushell.sh/book/pipelines.html#assigning-pipeline-results-with-let)).
- **Gotchas.** `$in` meaning depends on position (first position ⇒ block/filter input; elsewhere ⇒ previous expression's result; no input ⇒ `null`) and is scoped in sub-expressions ([Pipelines — When Does `$in` Change](https://www.nushell.sh/book/pipelines.html#when-does-in-change-and-when-can-it-be-reused)). Best practice: bind `$in` to a named variable at the top of a block. `let` of a stream collects it.
- **Candidate phrasing.** llang already has `set NAME to expr` / `let NAME be expr` and `nothing` for null; reuse them unchanged. For environment, add an explicit map rather than `$env.X`:
  - **`set environment to a map with "HOME" mapped to "/home/ada"`**, passed as a labeled argument to a shell call. Do **not** invent an implicit `$env` namespace that mutates globally. Bind pipeline input immediately (Nu's own best practice): **`set items to the incoming value`**.

### 3.6 Custom commands (functions)

- **Nu semantics.** `def name [params] { body }` creates a first-class command; the **last expression is implicitly returned**; there is no `return`/`echo` needed; `print` is for display ([Custom Commands](https://www.nushell.sh/book/custom_commands.html#creating-and-running-a-custom-command), [Returning Values](https://www.nushell.sh/book/custom_commands.html#returning-values-from-commands)). Commands can read pipeline input via `each`/`$in` and stream it ([Custom Commands — Pipeline Input](https://www.nushell.sh/book/custom_commands.html#pipeline-input)). Bodies can declare local `def`s (shadowing only within the block); duplicate `def` in one block is a parse error; custom commands shadow builtins and `%` bypasses the shadow ([Custom Commands — Defining a command more than once](https://www.nushell.sh/book/custom_commands.html#defining-a-command-more-than-once)). Input/output signatures (`int -> int`) are checked at parse time ([Custom Commands — Pipeline Input-Output Signature](https://www.nushell.sh/book/custom_commands.html#pipeline-input-output-signature)).
- **Gotchas.** A space is required between name and `[` (`def greet[name]` is a parse error); body must be a `{ ... }` block, not a variable holding a closure. `echo "msg"` in a non-final position is discarded — use `print`. An input/output signature body that ends with `print` fails ("command outputs nothing"). `--help` is reserved. `def --wrapped` forwards unknown flags to an external.
- **Candidate phrasing.** llang custom functions already have explicit `give back`, which is *safer* than implicit return and satisfies the "last value is the result" invariant without the discard trap:
  - ```
    define a function run checked taking command
        set result to call shell with command = command
        require item "exit code" of result equals 0, "command failed"
        give back item "output" of result
    end function
    ```
  - Enforce per-command label schemas as the analogue of Nu signatures; a "wrong type of input" should be a localized error, not silent coercion (`DESIGN.md` §5.3). When wrapping an external, prefer **argv lists** over a single command string (§6).

### 3.7 Modules

- **Nu semantics.** A module is a container of definitions (custom commands, aliases, constants, type aliases, externs, env, submodules). Import with `use <path> <import-pattern>`; import the whole module as a command-with-subcommands, `*` for all definitions, or selected members ([Using Modules — Overview / Module Definitions](https://www.nushell.sh/book/modules/using_modules.html)). Only definitions marked `export` (or `export-env`) are visible; others are private ([Creating Modules — Exports](https://www.nushell.sh/book/modules/creating_modules.html#exports)). `main` is the module-named export; an export may not share the module's name. A module's top level may contain **only definitions**, not arbitrary statements. Imports are **scoped to the block** they appear in; `export-env` runs on each `use`; submodules via `export module` vs `export use` differ in what plain `use <module>` imports ([Using Modules — Imports are scoped to their block](https://www.nushell.sh/book/modules/using_modules.html#imports-are-scoped-to-their-block); [Creating Modules — Submodules](https://www.nushell.sh/book/modules/creating_modules.html#submodules)).
- **Gotchas.** `use` and `cd` must be separate lines — `use` resolves at parse time, before a same-line `cd` runs. A module imported by bare name is cached (edits ignored) until a new shell; a path-form (`./x.nu`) re-reads ([Using Modules — Module Path](https://www.nushell.sh/book/modules/using_modules.html#module-path)). `export-env` only runs when `use` is *evaluated*, not when merely parsed in another module. Parser keywords can't be export names.
- **Candidate phrasing.** llang already ships this almost verbatim (`docs/FAMILY-PLAN.md` §libraries, `examples/modules.ll`):
  - **`use the shell module`** (a native llang module of shell helpers) and **`use the foreign shell module`** (the explicit host-execution bridge, mirroring `use the foreign json module`).
  - Qualified calls: **`call run from shell with command = "git status"`**; aliases via `also known as` (`GRAMMAR.md`). Module files remain `.ll` files exporting functions/maps; only `use` makes names visible (private-by-default is already true in our loader). Module paths and the foreign allowlist must be resolvable at lint time to honor invariant 7.

### 3.8 Error handling

- **Nu semantics.** Non-zero external exit ⇒ error; in a script, execution stops; `LAST_EXIT_CODE` / `complete` / `catch`'s `exit_code` field expose the code ([Stdout, Stderr, Exit Codes — Exit Code](https://www.nushell.sh/book/stdout_stderr_exit_codes.html#exit-code)). `try { … } catch {|e| … } finally { … }` handles errors; `exit` is not an error (finally runs, catch doesn't); Ctrl+C raises `Operation interrupted` and is catchable ([Pipelines — Failing External Commands](https://www.nushell.sh/book/pipelines.html#failing-external-commands-in-a-pipeline); [Stdout, Stderr, Exit Codes — Interrupting with Ctrl+C](https://www.nushell.sh/book/stdout_stderr_exit_codes.html#interrupting-with-ctrl-c)). Signals report negative codes; `complete` never populates `LAST_EXIT_CODE`.
- **Gotchas.** `display_errors.exit_code` controls only the message, not the failure. SIGPIPE never counts as a failure (`^yes | ^head`). `pipefail=false` changes which failures count — we keep the safe default. `do -i` does **not** make a failing external harmless when piped. Redirected output of a failing command can be lost ([Stdout, Stderr, Exit Codes](https://www.nushell.sh/book/stdout_stderr_exit_codes.html)).
- **Candidate phrasing.** Reuse llang's problem machinery (`GRAMMAR.md` `fail` / `expect` / `require`):
  ```
  expect
      set result to call shell with command = "cat missing.txt"
  if a problem of kind shell_failure occurs then
      show item "errors" of problem
  if nothing went wrong then
      show item "output" of result
  end expect
  ```
  Map: non-zero exit ⇒ problem kind **`shell_failure`** (carrying a map with `"exit code"`, `"output"`, `"errors"`); timeout ⇒ `shell_timeout`; denied command/path ⇒ `shell_denied`; decode failure ⇒ `shell_output_invalid`. `require` assertions validate assumptions (e.g. `require item "exit code" of result equals 0, "expected success"`). `finally` has no llang equivalent today — record the gap; do not fake it.

## 4. Nushell features we deliberately OMIT (and why)

Each omission is a scope decision, not an oversight; all are consistent with `DESIGN.md` §6 guardrails and `FAMILY-PLAN.md` tiering.

| Nushell feature | Omit? | Reason |
|---|---|---|
| Reedline line editor, keybindings, history, multi-line editing, completion menu | **Omit** | UI/terminal-emulator concern (§5), not shell semantics. `repl.py` already provides a minimal host line loop. |
| Coloring, theming, prompts, `display_output` hook, `table` rendering modes | **Omit** | Presentation, not semantics. llang `show` already renders structured values; no theming surface in the closed vocabulary. |
| Plugins (`plugin use`), MCP server, TUI builder, LSP/DAP | **Omit** | Process/binary ecosystem and editor integration; outside a tree-walking interpreter and outside the method's "one host" scope. |
| Dataframes and dataframe operations | **Omit** | A separate analytics compute engine with its own lazy/parallel semantics; not needed for command orchestration and would violate the small-core rule. |
| Background jobs, `par-each`, parallelism (including experimental options) | **Omit (v1)** | Concurrency changes evaluation order and determinism invariants; defer until the core is stable. |
| Overlays (`overlay use`, `hide`, layered scopes) | **Omit (v1)** | Modules + block-scoped `use` already cover organization; overlays add a second name-resolution model. |
| Hooks (`command_not_found`, `pre_execution`, env hooks) | **Omit** | Implicit global behavior conflicts with "explicit labeling" and the lint-before-execute model. |
| Custom completions, `extern` type/completion declarations | **Omit (v1)** | Editor convenience; signatures can be reintroduced later as labeled schemas if needed. |
| Rich value types: `binary`, `duration`, `filesize`, `datetime`, `range`, `cell-path`, `semver`, `glob` | **Omit most** | llang's dynamic core has numbers/text/lists/maps/nothing. Byte streams decode to text; exotic types need real semantics, not sugar. (Binary/datetime can be revisited as typed library values.) |
| Static type annotations, `type` aliases, input/output signatures | **Omit (v1)** | llang is dynamic; optional `expect`/`require` assertions play the "loud check" role. Revisit only if a typed tier (L2) is built (`FAMILY-PLAN.md`). |
| Bash-compat operators (`&&`, `\|\|`, `2>`, `2>&1`), `^`/`%` sigils, `o+e>` token soup | **Omit by design** | Re-expressed as labeled parameters and explicit problem handling; avoids importing Nushell's own documented confusion. |
| Broad `open`/`save` format matrix (JSON/TOML/YAML/SQLite/CSV…) | **Partially adopt** | Keep a small, explicit codec set (llang already has `json` via the foreign bridge); add formats behind labeled library functions, never implicit extension-based magic. |
| `eval`, dynamic `source` of generated files, `source-env` | **Omit** | Directly contrary to parse-before-eval (invariant 7) and to llang's reject-don't-guess philosophy. |

## 5. Shell layer vs. terminal-emulator layer

These are two different layers and must not be conflated.

- **SHELL layer (what we are rebuilding).** A *semantic* layer: command/argv model, pipeline data flow, structured results (stdout / stderr / exit code as data), environment/cwd scoping, module and custom-command structure, resolution rules, and error/problem semantics — all expressible in llang values (numbers, text, lists, maps, `nothing`) and all testable without a screen. It talks to the host through process APIs (spawn with argv, capture streams, collect exit status). This document grounds *this* layer.

- **TERMINAL EMULATOR layer (out of scope).** A *graphics/UI* layer: the event loop, window and font rendering, ANSI/control-sequence interpretation, cursor and scrollback state, PTY management, mouse/keyboard event routing, color themes, and the interactive prompt/line editor (Nushell's reedline, keybindings, completions — see [Working with the Terminal](https://www.nushell.sh/book/terminal.html), [Reedline](https://www.nushell.sh/book/line_editor.html), [Coloring and Theming](https://www.nushell.sh/book/coloring_and_theming.html)). It answers "what pixels appear and what keystrokes arrive," not "what does a command mean." Nushell's own docs treat these as separate chapters ([Nu as a Shell](https://www.nushell.sh/book/nu_as_a_shell.html)).

**Why the emulator is out of scope for llang today.** (1) llang is a language/runtime, not an application; its consumer is an AI writing structured pseudocode (`DESIGN.md` §8), not a human at a rendered terminal. (2) The existing `repl.py` is a line-oriented host loop, sufficient to drive programs, and is not an emulator — we neither need nor should fake one. (3) A real emulator is a large, orthogonal engineering effort (graphics, input, terminal protocols) with no bearing on the semantic matrix, and would violate the small-core / thin-slice guardrails (`DESIGN.md` §6, `METHOD.md` "thin end-to-end vertical slice"). (4) Shell semantics are fully testable headlessly by capturing streams and exit codes. Consequence: llang shell calls consume/produce **text and structured data**, never "a terminal screen"; any future emulator would be a separate consumer of the same shell layer, not part of it.

## 6. Safety model for executing host commands from llang

Host execution is the highest-risk feature; it is deliberately an **explicitly labeled opt-in foreign bridge**, consistent with `src/llang/foreign.py` (docstring: "explicitly FOREIGN … allowlisted … values cross the boundary as ordinary Python numbers, texts, lists and maps") and `docs/FAMILY-PLAN.md` ("Interop leak → allowlist, explicit `foreign` marking, no implicit host-object access").

1. **Opt-in, never implicit.** Host commands are reachable only after `use the foreign shell module` and only via qualified calls (`call ... from shell`). A bare name never falls through to a host executable (unlike Nu's PATH fallback — invariant 9). No ambient shell interpretation of llang source.
2. **Allowlisted operations.** The shell bridge exposes a small registry of *operations* (e.g. `run`, `output`, `environment`) with a fixed label schema, mirroring `FOREIGN_FUNCTIONS` / `FOREIGN_CONSTANTS` in `foreign.py`. Unknown command names, labels, or flags are rejected at lint/parse time with "did you mean …" (invariants 7–8; `METHOD.md` "validate every label against a registry").
3. **argv, not interpolated shell strings.** Prefer `program = "git", arguments = a list of "status", "--short"` over `command = "git status --short"`. The ideal is never to use a host shell (`shell=True`) to evaluate a llang-supplied string. **Implementation exception:** the shipped `src/llang/foreign.py` uses `shell=True` for `run command` so shell builtins such as `dir`/`echo` work cross-platform; this is a documented deviation, disclosed in `SECURITY.md`, and `call build from shell ...` provides the safer argv-style path. New code should prefer the argv form.
4. **Typed boundary values.** Values cross as llang primitives (text/number/list/map/nothing); decode external bytes as UTF-8 with a defined policy (replacement char, or a `shell_output_invalid` problem under `--strict`-like opt-in); no host objects leak into llang. Match Nu's rule that records/filesizes/etc. cannot be implicitly converted to argv ([Running External Commands — Values that aren't strings](https://www.nushell.sh/book/running_externals.html#values-that-aren-t-strings)).
5. **Scoped environment and cwd.** By default, the child inherits a snapshot; any cwd/env changes are local to the call and discarded (Nu closure/def scoping — invariant 6). Persistence into subsequent llang statements requires an explicit labeled opt-in (e.g. `keep environment = true`) and should be lint-visible. No implicit global mutation.
6. **Three-channel result, fail-safe.** Every host call returns a map with `"output"`, `"errors"`, `"exit code"` (capture by default; text or `nothing`). Non-zero exit ⇒ `shell_failure` problem (pipefail-style); timeouts ⇒ `shell_timeout`; denied operation ⇒ `shell_denied`. Never silently conflate stderr with output, and never treat a non-zero exit as success just because text was produced.
7. **Resource limits.** Mandatory timeout, bounded output capture (truncate with an explicit marker, or fail), and bounded process count. This is the practical guard against infinite streams (`1.. | …` needs an explicit `first`) and memory blow-ups from collecting streams — Nu documents both hazards ([Pipelines — Collectability of `$in`](https://www.nushell.sh/book/pipelines.html#collectability-of-in); [Custom Commands — Streaming and collecting input](https://www.nushell.sh/book/custom_commands.html#streaming-and-collecting-input)).
8. **Path and program restrictions.** Programs resolve from a configurable allowlist, not arbitrary PATH search; relative paths resolve against the scoped cwd; reject path traversal outside permitted roots. Mirror Nu's explicit resolution discipline but stricter (no implicit external fallback).
9. **Loud, source-located diagnostics.** Denials, timeouts, bad labels, decode failures, and non-zero exits become localized llang problems via `expect`/`fail`, never warnings printed and ignored. Secrets in argv/environment should be redacted in diagnostics.
10. **No dynamic execution of generated source.** `eval`/dynamic `source` is absent (invariant 7); a path used by a shell-related module import must be a static constant. This keeps the attack surface — strings reaching a host process — enumerable at lint time.

**Design warning (carry over from `python-semantics.md` and `DESIGN.md`):** prefer rejecting to guessing. A shell call with an unknown label, an unexpected type, or an ambiguous program must fail at lint/parse time where possible; at runtime it must fail loudly with a problem kind. The foreign marking is the user-visible promise that "this reached the host," and must never be implicit.
