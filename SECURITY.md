# Security policy

## Scope

llang is an interpreter and developer tool. Its most powerful capability is the
opt-in foreign `shell` module, which executes host commands.

## Threat model

- llang programs are treated as **untrusted code**, especially when generated by an AI.
- Nothing in the core language can access the host, spawn processes, or read files
  beyond the explicitly allowlisted `read text from` / `write text to` builtins.
- Foreign modules require an explicit `use the foreign <name> module` line; there is
  no implicit host access.
- The `shell` module is the only bridge that can execute processes. It also exposes
  `environment value`, which reads arbitrary host environment variables (including
  secrets such as tokens), and an optional `directory` label that sets the child
  process's working directory. Treat any program using this module as fully trusted.

## Current safeguards

- Foreign modules are an allowlist in `src/llang/foreign.py`.
- `run command from shell` takes the command as visible text and captures all
  three channels (exit code, stdout, stderr). `output of command` and
  `command succeeds` collapse that result to text or a boolean.
- The default timeout is 30 seconds and can be overridden by the caller; there is
  currently no hard upper bound.
- Path and command strings must be text; no host objects cross the boundary.
- Every foreign call goes through the same labeled-argument validation as builtins.

## Known limitations

- The shell bridge uses `shell=True` on the host, so shell metacharacters in a
  command string are interpreted by that shell. This is a deliberate, documented
  exception to the design note in `docs/research/terminal-semantics.md`; prefer
  `call build from shell with program = ..., args = ...`, which quotes arguments
  using the llang `shlex` rewrite.
- `environment value` can expose secrets from the host process environment to an
  llang program. Avoid it in programs that process untrusted input.
- `read text from` / `write text to` have no sandbox or path policy.
- Unhandled host `OSError`s are wrapped with source locations, but no permission
  model is enforced.

## Reporting

Please report security issues privately to the maintainers rather than opening a
public issue. Include a minimal reproducer and the affected version.
